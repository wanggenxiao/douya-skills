# MinerU PDF → Markdown 转录

## 用途

把 PDF 转成 LLM 友好的 Markdown，自动处理：
- 扫描件 OCR（109 种语言）
- LaTeX 公式
- HTML 表格（支持跨页合并）
- 多栏版面、阅读顺序重排
- 页眉页脚自动剥除
- 抽出图片到子目录

输出文件：`<输出目录>/<pdf名>/auto/<pdf名>.md` + `images/` 子目录。

## 关键事实（必读）

**MinerU 桌面客户端 ≠ 本地 CLI**：
- 桌面客户端走 mineru.net **云服务**，免费配额 **200 页**，超出报错"number of pages exceeds limit (200 pages)"
- 本 skill 用的是 `pip install mineru` 的**本地版**，跑在用户电脑上，默认上限 1000 页，且可改 `--max-convert-pages 99999` 实际无限制

用户报"200 页限制"时，提醒他用这个 skill（本地版）而不是桌面客户端。

## ★ MinerU 2.x / 4.x 双版本自适应（2026-09-18）

**MinerU 4.0 把 CLI 彻底改了**，2.x 的写法在 4.0 上完全无效——这是学员反馈"skill 调不起来"的根因。
`run_mineru.py` 现在会**自动探测本机装的是哪一版**，按版本构造命令，**对外参数不变**。

| 概念 | 2.x | 4.x |
|:--|:--|:--|
| 命令名 | `mineru` | `mineru` 或 `mineru-kit`（互为别名） |
| 子命令 | 无 | `parse` |
| 输入 | `-p <pdf>` | 位置参数 `<pdf>` |
| **输出** | `-o <目录>` | **`-o <文件.md>`** ← 语义变了 |
| 质量 | `-b pipeline/vlm-*` | `--tier flash/basic/standard/advanced` |
| 页范围 | `-s 0 -e 49`（**0-based**） | `--pages 1-50`（**1-based 闭区间**） |
| 语言/解析方式 | `-l ch` / `-m auto` | 无，统一并入 `--tier` |

⚠ **官方 README 里没有 `--ocr-mode` 这个参数**，看到有人这么用先核实再抄。
⚠ 官方明确提示：**别拿 `flash` 当最终阅读质量**（只适合建索引/检索）。

**排障**：`--dry-run` 只打印命令不执行；`--force-major 2|4` 跳过探测强制指定版本。
换版本或报"未知参数"时，先 `--dry-run` 把命令打出来核对。

## 调用方式

直接调脚本（PowerShell/Bash 都行）：

```bash
"C:/Users/Administrator/.claude/skills/mineru-pdf-to-markdown/venv/Scripts/python.exe" \
  "C:/Users/Administrator/.claude/skills/mineru-pdf-to-markdown/scripts/run_mineru.py" \
  --pdf "C:/path/to/input.pdf" \
  [--out "C:/path/to/output_dir"] \
  [--tier standard|advanced] \
  [--start 0] [--end 50] \
  [--dry-run]
```

参数：
- `--pdf` (必填): PDF 绝对路径
- `--out` (可选): 输出目录，默认 `<PDF所在目录>/<PDF名>_mineru/`
- `--tier` (可选，**4.x**): 解析质量，默认 `standard`。
  **国标规范、图纸这类表格公式多的难文档用 `advanced`**；`flash` 只适合建索引，别当最终稿
- `--start`/`--end` (可选): **0-based** 页号区间（4.x 下脚本会自动 +1 转成 1-based，不用自己换算）
- `--dry-run` (可选): 只打印命令不执行，换版本/排障时先用它核对
- `--force-major 2|4` (可选): 跳过自动探测，强制按该版本构造命令
- 以下仅 **2.x** 生效，4.x 下会提示并忽略：
  - `--backend`: `pipeline`（默认）或 `vlm-auto-engine`（GPU 高精度）
  - `--lang`: OCR 语言，默认 `ch`（中英混合）
  - `--method`: `auto`（默认）/ `txt` / `ocr`

主动触发：
- 用户说"把这个 PDF 转 markdown"、"PDF 转录"、"PDF 提取文字"、"扫描件识别"、"OCR 这个 PDF"
- 用户上传 PDF 并问"你看看里面写了什么"——先转录再 Read
- 用户抱怨"MinerU 桌面客户端 200 页限制"

间接触发（AI 需要读 PDF 内容时）：
- PDF 体量大（>50 页）或图像扫描件，单纯 Read 拿不到结构化内容
- 后续 skill 需要 PDF 的文本/表格（地勘报告、规范、参考论文）
- **小型纯文本 PDF（<20 页且可搜索）**：直接用 Read 工具的 pages 参数即可，**不要**杀鸡用 MinerU

## 输出位置铁律（2026-09-15 收紧，比照全局 DOC→DOCX / DWG→DXF）

**转录产物一律放在原 PDF 同一目录下，与原件并排。**
**即不传 `--out` 就是对的，不要画蛇添足指到别处。**

默认输出目录都是 `<PDF父目录>/<PDF名>_mineru/`，但**里面的结构两版不同**：
- **2.x**：`<PDF名>_mineru/<PDF名>/auto/<PDF名>.md` + `images/`
- **4.x**：`<PDF名>_mineru/<PDF名>.md`（`-o` 直接指向该文件）

→ 所以**别把产物路径写死在别的脚本里**，要找 md 就 `rglob("*.md")`。

理由与 DOC→DOCX、DWG→DXF 完全一致：转录 md 是**资料的可读版本、属于项目档案**，
用户要能在原件旁边直接打开核对，后续别的 AI 会话也要能在原件旁找到它。

- ❌ **禁止**把转录产物丢进 `_scratch`。它不是"调试中间品"，哪怕这次只是试跑。
  （真正的一次性调试脚本才进 `_scratch`。）
- ✅ 校核产物（`_check_报告.md` / `_check_pages/`）跟着 md 一起并排放，不单独拆走。
- ✅ 原件目录已有转录文件夹的，**并入它**，不要再造第二个。
- 只有原件目录不可写时才退 `_scratch`，并在回复里说明。
- 用户明示"输出到 XX"时按用户指定路径。

**完成转换后在回复正文知会用户一声**（如"转录已放在原 PDF 同目录的 XXX 下"），
让用户一眼确认没跳步。

## 后端选择建议

| 场景 | 推荐 backend | 原因 |
|---|---|---|
| 中文规范/教材/可搜索 PDF | `pipeline` | 快、稳、CPU 也行，对扫描件已有 OCR |
| 含复杂公式（数学/物理/工科教材） | `vlm-auto-engine` | MinerU2.5-Pro 视觉大模型，公式识别明显优于经典 OCR |
| 大量跨页表格、复杂排版 | `vlm-auto-engine` | VLM 对版面理解更强 |
| 几百页大书 | `pipeline` | VLM 慢，pipeline 性价比高 |

## 200 页限制怎么解决

**不需要解决** —— 本地 CLI 默认上限就是 1000 页，且可通过 `--max-convert-pages 99999` 进一步提高。这个 skill 已经把这一项写进 wrapper 默认参数。

如果遇到 GPU 显存爆掉（10000+ 页极端情况），可以分段：
```bash
python run_mineru.py --pdf big.pdf --start 0 --end 199
python run_mineru.py --pdf big.pdf --start 200 --end 399
# ... 最后合并 markdown
```

## 转换后强制校核（2026-09-15 定为铁律，不可跳过）

**核心认知：MinerU 的错是「看上去完全正常的错」。** 读一遍 md 觉得通顺 = 无效检查（包括 AI 自己读）。
要发现不一致，必须引入**独立于 MinerU 的第二数据源**做对照。以下所有措施都是这一条的变体。

### 第 0 步：能绕开就别让它出错（优先级最高，属预防不属检查）

- **源头是 docx 的**：表格一律回 `word/document.xml` 逐格读（含 `<w:vMerge/>` 合并标记）生成，
  **不用 MinerU 的表格识别**。MinerU 只负责正文叙述。这条能用就必须用。
- **Word 导出的 PDF（有文本层）**：正文加 `--method txt` 强制文本提取，不走 OCR，错字率归零。

### 第 1 步：转完立刻跑校核脚本（无条件，不问用户）

```bash
"C:/Users/Administrator/.claude/skills/mineru-pdf-to-markdown/verify_venv/Scripts/python.exe" \
  "C:/Users/Administrator/.claude/skills/mineru-pdf-to-markdown/scripts/verify_transcription.py" \
  --pdf "<原PDF>" --md "<产出.md>" [--md2 "<第二后端.md>"] [--render]
```

**注意用的是 `verify_venv` 不是 `venv`** —— pdfplumber 与 mineru 的 pypdfium2/pdftext 版本冲突，
故意隔离成两个环境，**绝不要把 pdfplumber 装进 mineru 的 venv**（会把 mineru 依赖搞坏）。

脚本做 5 件事，产出 `_check_报告.md` + 必看原页清单：

| # | 检查 | 抓什么 | 局限 |
|---|---|---|---|
| 1 | 体检 | 整块内容丢失、md 近空、图片 0 张、`2..5`/乱码等事故特征 | 只抓大事故 |
| 2 | 高危 token 逐页对照 | 数字 / `≤≥<>` / 罗马数字 / `°‰㎡` 缺失 → 定位到页 | **仅有文本层可用** |
| 3 | 双后端交叉 | pipeline vs vlm 两份 md diff，分歧处=高风险点 | 扫描件唯一自动化手段，耗时翻倍 |
| 4 | 表格结构对照 | pdfplumber 行×列 vs MinerU HTML 表行×列 | 维度对得上≠归属对，仍需看原页 |
| 5 | 公式页定位 | 列出含公式页 + LaTeX 片段数 | **正确性无法自动验证** |

### 第 1b 步：规范/标准类文档必跑骨架校验（专治「整块丢失」）

```bash
"<skill>/verify_venv/Scripts/python.exe" "<skill>/scripts/check_skeleton.py" --md "<产出.md>"
```

**为什么必须单独有这一步**：`verify_transcription.py` 和「按需核对」都防不住**内容整块丢失**——
丢了的东西在 md 里不留痕迹，读起来依然通顺，人根本不会想到去核那一页
（实例：土钉墙一组配筋公式整段消失、湖北地标表的「注1」整行消失）。

规范类文档的救命特性是**条文号/表号/图号严格连续**，断号=那段没了。纯机器可判、零人工、全库可跑。
输出 `_check_骨架.md`。适用国标/行标/地标/规程；普通图书论文不适用（抽不到编号会自己声明）。

**读报告的三条要点**：
1. **「疑似误抽」不是错**：MinerU 常把编号与正文连写（`11.9.2` + 正文首字「8度」→ 粘成 `11.9.28`），
   脚本按「组内连续段之后的孤立大号」识别并剔除。
2. **断号要回原件确认再下结论**：规范**本身就会跳号**。实测 GB 50010 图号从 6.2.11 直接跳到 6.2.15，
   6.2.12~14 原文就不存在——**先怀疑原文跳号，再怀疑转录丢失**。
3. **已知局限**：规范末尾的「条文说明」会重复全部条文号，可能**掩盖正文里的缺失**
   （正文缺 6.2.3 但条文说明有 → 不报）。要严格查就把条文说明部分切掉单独跑。

**实测（GB 50010，441 页）**：抽到条文号 1165 条，**条文号零断号**——正文无整块丢失；
17 处异常全是「疑似误抽」或原文跳号。注意正则必须容忍**编号与正文无空格连写**，
否则抽取率会从 1165 掉到 61，报告完全不可信。

### 脚本自身的两个已知特性（别误读报告）

1. **LaTeX 归一化已内置**：MinerU 会把 `×`→`\times`、`1.90`→`1 . 9 0`，不归一化就满屏误报。
   脚本已做符号映射 + 去空格。若日后发现新的误报符号，补 `LATEX_MAP` 而不是放宽阈值。
2. **pdfplumber 只认框线表**：无框线表 / 公式排版表它检出 0 个，此时报告给 ℹ 提示
   并把全部页列入必看，**不判红灯**。反过来说，这类文档的表格**没有任何自动化保护**，只能肉眼。

### 有效性实证（2026-09-15 首跑）

样本：9 页土钉墙计算书（公式密集、无框线表）。
检查 2 报「第 7/8 页缺 `103`、`360`」→ 回原页核实，PDF 上是
`A_s = 1.6×13.42×10³/360` 一组四个配筋公式，**MinerU 输出里整段丢失**。
这是纯读 md 绝对发现不了的错（丢的内容不留痕迹，上下文依然通顺）。
→ 检查 2 是目前性价比最高的一项，有文本层就必须跑。

### 回归测试：湖北地标安全等级表（2026-09-15，带标准答案）

素材：`AI社群/交付内容/02-1_让AI读懂你的资料/素材/湖北地标_安全等级表_节选5页.pdf`
（同目录有 docx 原件 + `_素材说明.md` 标准答案）。**改动本 skill 后拿它回归。**

| 错型 | 自动化能否抓到 | 证据 |
|---|---|---|
| 比较符退化 `H≤30`→`H<30` | ✅ 检查 2 抓到 | 报告「第 3 页缺 ≤(缺3)」 |
| 罗马数字 `Ⅲ或Ⅳ`→`IⅢ或IV` | ✅ 检查 2 抓到 | 报告「缺 Ⅰ Ⅳ Ⅴ」 |
| **合并单元格错位** | ❌ **完全抓不到** | 检查 4 显示 PDF=(19,5) md=(19,5) **完全一致、判通过** |
| **整行丢失（表下"注"行）** | ❌ 抓不到 | pdfplumber 也漏算该行，两边一致 = 假通过 |

**必须记住的两条局限**：
1. 行×列一致 ≠ 内容归属正确。19 行里有 12 行的安全等级整体下移一行
   （原件「很严重→一」全被转成「很严重→二」），结构维度完全看不出来。
2. **对照双方可能同时漏掉同一内容**：原件表实为 20 行（末行是长段"注"），
   MinerU 和 pdfplumber 都只算 19 行，于是"对上了"。
   → 检查 4 通过**不构成任何保证**，只有看原页算数。

**第 0 步有效性实证**：同一张表改从 docx XML 抽（含 `<w:vMerge/>` 标记），
20 行全部正确——等级、`≤`、罗马数字、注行一个不差。
→ **有 docx 就别让 MinerU 碰表格**，这是唯一能把错误率打到 0 的办法。

### 大文件实测（441 页《混凝土结构设计规范》GB 50010，2026-09-15）

**性能基准（可直接报给用户）**：441 页 / pipeline / RTX 3080 = **258 秒（约 1.7 页/秒）**，
经验值 **100 页 ≈ 1 分钟**。校核脚本再跑 **52 秒**。

**产物体积要注意**：441 页产出 **125 MB**，其中有用的只有 md(0.9MB) + images(7.6MB)；
`_layout.pdf`/`_span.pdf`/`_origin.pdf`/`_middle.json`/`_model.json`/`_content_list.json`
共 **117 MB 是调试副产品**（`_origin.pdf` 还是原 PDF 的重复副本）。
→ **大文件转完主动问用户要不要清掉这 6 个调试文件**，否则转几本规范就是上 G 的冗余，
OB 库还会跟着同步。

**这份文件推翻了一个预判**：它是扫描件 OCR 过的，自带脏文本层（PDF 里"混凝土"写成"泪凝土"）。
原以为 MinerU 会沿用脏文本层把错字继承下来——**实测没有**，md 里"泪凝土"0 次、"混凝土"1660 次全对。
MinerU 自己重认了一遍，**比原 PDF 自带的文本层还准**。
→ 副作用：检查 2 拿脏文本层当"标准"去比 MinerU 的正确输出，会**大量假警报**。

**这轮实测修掉的 8 个假警报源**（改脚本时别改回去）：

| # | 假警报源 | 处置 |
|---|---|---|
| ① | 印刷页码（MinerU 默认剥页眉页脚）→ 200+ 页每页报"缺页码" | 抽文本时剥掉页眉页脚行 |
| ② | 目录页点线页码 | 整页跳过（数点线 ≥5 判定；行会被坐标聚类切碎，**不能按行尾判**） |
| ③ | `二a类`/`三a类`（规范标准术语）被判 OCR 事故 | 删掉"中文间夹单字母"规则 |
| ④ | pdfplumber 按行拼接使表格数字粘连成 `110.0113` | 改 `extract_words` 保词边界 |
| ⑤ | 粘连仍无法根治的数值密集页 | 单页缺 ≥8 项 → 折叠成"对照不可靠，整页人工看" |
| ⑥ | 全角 `＜` vs 半角 `<` | 全角半角归一后再比 |
| ⑦ | 表格数不等时 zip 逐表配对**全部错位**，之后每张表都报 ⚠ | 数量不等就不配对，只报数量差 + 两侧形状 |
| ⑧ | 必看清单列 300 页 = 没有优先级 | 分 A/B/C 三档 + 页码封顶 25 个 |

**最重要的一条教训——大文件上校核报告会退化**：
即便修完上面 8 项，这份文档的 A 档仍有 117 页、C 档 95 页。
**别假装能逐页核完**。清单覆盖过半篇幅时报告会自动打出提示，此时正确做法是
**按需核**：用到哪一页的表/公式，当场回那一页确认，其余一律标「仅据转录、待核」。

### 第 2 步：看原页（唯一能抓 ★★★ 合并单元格错位的手段）

**铁律：凡要引用表格或公式的内容，必须先看原页，无例外。**
不是"要下结论时才看"——地标那次 AI 就没意识到自己在下结论。
前面的自动化只决定我要看 3 页还是 300 页，不能替代看。

- `--render` 会把必看页渲染成 PNG（已内置 ≤1600px 限制，遵守全局图片铁律）直接 Read。
- 检查 2/3 全绿也不能免除看表页：**文字全对、归属关系错**的错型对 token 对照完全隐形。

### 第 3 步：留痕

`_check_报告.md` 必须留在产物目录（不删），下游结论逐条标注
「已回原件核实」或「仅据转录、待核」。

### 按源类型分流（照此执行）

| 源 | 动作 |
|---|---|
| docx 转的 PDF | 表格走 XML + `--method txt`；跑脚本；基本无需看原页 |
| 有文本层 PDF | 跑脚本（检查 1/2/4/5）；引用表格公式 → 看原页 |
| 扫描件 | 跑脚本 + **必须补跑第二后端给 `--md2`**；分歧点 + 所有表/公式页看原页 |

**唯一例外**：用户明说"只要个大概/随便看看内容"，可只跑第 1 步、跳过看原页，
但必须在回复里讲明"未核对原件"。

## 输出可信度红线（2026-07-02 实战教训，必读）

**MinerU 输出的表格和公式不能直接当"事实"引用**，尤其在审查、核对、比价、出报告这类"错一个字就出事"的下游任务里。实证案例：湖北边坡地标征求意见稿（docx→PDF→MinerU），安全等级表"很严重→一级"被转成"很严重→二级"，AI 据此报了"地标违反国标"的重磅假意见，被用户当场抓包。

按错型分级：

| 错型 | 表现 | 危险度 |
|---|---|---|
| **合并单元格错位** | 纵向合并（rowspan）多的表，某列整体上/下漂移一行，文字全对但**单元格归属关系错**；渲染出来毫无违和感，最会骗人 | ★★★ |
| 比较符退化 | `≤`→`<`、`≥`→`>`（凭空制造"边界缺档"假象） | ★★★ |
| 罗马数字 | `Ⅳ`→`V`、`Ⅲ`→`IⅢ`（制造"缺级/多级"假象） | ★★ |
| 符号丢失 | `°` 丢、下标错乱、`2.5`→`2..5` | ★★ |
| 公式 OCR | LaTeX 对错混杂，无法从输出本身分辨 | ★★★ |

**核对铁律**（触发条件见上节「转换后强制校核」——默认必做，不是"要下结论时才做"）：

1. **源头是 docx 的，表格一律回 docx XML 核对**，不要信 MinerU 的 HTML 表。解包 `word/document.xml`，按 `<w:tr>/<w:tc>` 逐格打印，`<w:vMerge/>` 标记合并结构：
   ```python
   import zipfile, re
   doc = zipfile.ZipFile(docx).read('word/document.xml').decode('utf-8')
   # 按内容关键词定位表格后, findall(r'<w:tr[ >].*?</w:tr>') 逐行,
   # 每格 ''.join(findall(r'<w:t[^>]*>([^<]*)</w:t>')), 'vMerge' in cell 标记 [V]
   ```
   甚至更进一步：docx 来源的转录，**表格可以直接从 XML 生成、跳过 MinerU 的表格识别**。
2. **公式**（docx 里常是 WMF/公式编辑器图片，XML 无文本）：用 pypdfium2 定位页码（`get_textpage().get_text_bounded()` 搜正文关键词）+ `render(scale=4~5)` 裁横带出 PNG（≤1900px）**肉眼核对原页**。同结构公式对（静力版 vs 地震版）的内部一致性对比是发现"原文真错"的利器，但两式都要看原页。
3. 交付审查/核对类结论时，每条注明"已回原件核实"还是"仅据转录、待核"。
4. 遇到"边界缺档、缺级、表逻辑矛盾"这类反常发现，**先怀疑转录错，后怀疑原文错**。

## 批量建库模式（几百~几千份规范转 Markdown 库，2026-09-15 定，待触发）

**触发口令**：用户说"建规范库 / 批量转几百份 / 给国标建 markdown 数据库 /
做 RAG 知识库 / 把这一整个文件夹的规范都转了"——即**转录对象是"一批"而不是"一份"**时，
走本节，不要按单份流程逐个转完就交差。

### 先摆正目标（这一句决定后面所有设计）

> 批量建库的目标**不是**「保证每一页都对」（1000 份 × 400 页 = 40 万页，人工核不可能），
> 而是「**错误可发现、可追溯、不致命**」。

单份流程那套"必看原页清单"在这个量级直接失效——**别把它套过来**。

### 五层方案（按投入产出比排序，前三层是一次性开发、全库复用）

**第一层 · 页码锚点（最重要，成本最低）**
给 md 每段标上它来自原 PDF 第几页，将来检索到某条规范能一键跳回原件那一页。
**不追求转对，追求可回溯**——这一层的价值超过后面所有层。
- 数据源：MinerU 的 `<名>_content_list.json`，每个内容块都带 `page_idx`。
- ⚠ **与「大文件清调试文件」规则冲突，建库模式下优先本条**：
  `_content_list.json` **必须保留**（或先抽出页码映射再删），
  `_layout.pdf`/`_span.pdf`/`_origin.pdf`/`_middle.json`/`_model.json` 仍可删。
- 尚未写成脚本，触发时现做（读 json → 按 page_idx 给 md 分段插锚点）。

**第二层 · 骨架完整性校验（专治整块丢失）**
`check_skeleton.py`，**已实现**，见上文「第 1b 步」。全库可跑、秒级、零人工。
这是唯一能自动发现"内容整段消失"的手段，批量场景必跑。

**第三层 · 按源分流（比提高单一流程精度更有效）**

| 类型 | 处理 | 预期错误率 |
|---|---|---|
| 官方电子版（文字可复制） | `--method txt` 走文本层，不 OCR | 很低 |
| 有 docx / 官方结构化源 | 表格走 XML（见第 0 步） | 表格近乎零错 |
| 扫描件（如 GB 50010） | 必须双后端交叉（`--md2`） | 高，重点关照 |

先分堆再动手。库里往往一半是可搜索 PDF，这部分几乎不用操心，**把精力集中在扫描件那堆**。

**第四层 · 抽样审计 + 质量标签**
每份随机抽 5~10 页人工核，按结果给文档打标，**标签随数据走**：
- **A 级**（骨架完整 + 抽样零错）→ 正文可直接信
- **B 级**（零星错）→ 可用，但表格数值须回原件
- **C 级**（骨架断号 / 抽样错多）→ 换 `vlm-auto-engine` 重转，或标记"仅作检索入口，不作依据"

**第五层 · 表格单独对待（核心建议）**
表格是**错误率最高 + 后果最严重 + 最检测不出来**的那一类（本 skill 三个实例全是表格）。
建库时**把表格从正文拆出来单独存，并默认全部标记「须回原件确认」**。
正文叙述可进 RAG 当事实源，**表格里的数值不行**。
理由：查规范十次有八次问"某条文怎么说"（转录质量够用），剩下两次问"某系数取多少"——
那正是最容易错、错了最致命的地方，强制回原件的代价极小、收益极大。

### 落地顺序

**第一层 → 第二层 → 第三层**（全自动化、一次开发、全库复用），做完库就具备
"错了能发现、能追溯"的底子；第四、五层是持续投入，边用边补。

### 批量场景下这些单份规则要改

- ❌ 不要对每份都生成「必看原页清单」并试图看完——改为骨架校验 + 抽样审计。
- ❌ 不要无脑删调试产物——`_content_list.json` 是页码锚点的命根子（见第一层）。
- ✅ 输出位置铁律照旧：每份的转录仍与其原件并排。
- ✅ 性能预估照旧：**100 页 ≈ 1 分钟**（pipeline/RTX 3080），1000 份 × 300 页 ≈ 50 小时，
  **先告诉用户这个数**再开工，别闷头跑一夜。

## 故障排查

- 报错 `CUDA out of memory`：换 `--backend pipeline`，或分段
- 中文识别错乱：确认 `--lang ch`
- 表格识别差：换 `--backend vlm-auto-engine`
- 首次运行很慢：在下载模型（pipeline ~1GB，vlm ~2GB），下载到 `~/.cache/modelscope` 或 `~/.cache/huggingface`，之后秒开
