# MinerU PDF → Markdown 转录

## 用途

把 PDF 转成 AI 友好的 Markdown，自动处理：扫描件 OCR（109 种语言）、LaTeX 公式、HTML 表格（支持跨页合并）、多栏版面阅读顺序重排、页眉页脚剥除、图片抽取到子目录。

输出：`<输出目录>/<pdf名>/auto/<pdf名>.md` + `images/` 子目录。

## 关键事实（必读）

**MinerU 桌面客户端 ≠ 本地版，这是两个东西：**

| | 桌面客户端 | 本地版（本 skill） |
|---|---|---|
| 算力在哪 | mineru.net **云服务器** | **你自己的电脑** |
| 页数 | 免费配额 **200 页**，超了报 `number of pages exceeds limit (200 pages)` | 默认 1000 页，本 skill 已调到 99999，**实际无限** |
| 装法 | 下客户端，双击 | `pip install mineru`，一条命令 |
| 资料上不上云 | **上传到云端** | **完全不出本机** |

> ⚠ 本地版**不是破解版**，是 MinerU 官方开源的同一个项目，只是跑在你自己机器上。
> ⚠ 对**涉密/敏感资料**，只能用本地版——客户端会把文件传到云端。

**首次使用前必须先装环境**，见同目录 `README.md`。没装环境，这个 skill 只是一份说明书。

## 调用方式

```bash
<mineru环境的python> <本skill目录>/scripts/run_mineru.py \
  --pdf "要转的文件.pdf" \
  [--out "输出目录"] \
  [--backend pipeline|vlm-auto-engine] \
  [--lang ch|en|auto] \
  [--method auto|txt|ocr] \
  [--start 0] [--end 50]
```

脚本会自动在**本 skill 目录下的 `venv/`** 里找 mineru；找不到就退回系统 PATH。所以两种装法都支持：装进 skill 自带 venv，或装进你自己的 Python 环境。

参数：
- `--pdf`（必填）：PDF 路径
- `--out`：输出目录，默认 `<PDF所在目录>/<PDF名>_mineru/`
- `--backend`：`pipeline`（默认，快稳，CPU 也能跑）｜`vlm-auto-engine`（GPU 高精度，公式表格更准，首跑要下 2GB 模型）
- `--lang`：OCR 语言，默认 `ch`（中英混合），纯英文用 `en`
- `--method`：`auto`（默认自动判断要不要 OCR）｜`txt`（强制文本提取）｜`ocr`（强制 OCR）
- `--start`/`--end`：0-based 页号区间，分段转时用

## ★先判断文件类型，别无脑 OCR

| 文件 | 该怎么做 | 为什么 |
|---|---|---|
| **Word（.docx）** | **根本不用 MinerU**，直接读 | docx 本身就是结构化的，准确率 100%。拿 OCR 转 Word 是**把对的弄错** |
| **文字型 PDF**（能选中复制文字） | `--method txt` | 直接抽文本，**零错误** |
| **扫描件 PDF**（整页是图） | `--method ocr` | 只有这种才真的需要 OCR |
| 小型可搜索 PDF（<20 页） | 直接让 AI 读，别杀鸡用牛刀 | — |

> **口诀：能直接读的就别 OCR，能走原文件的就别走图片。**

## 后端选择

| 场景 | backend | 原因 |
|---|---|---|
| 中文规范/教材/可搜索 PDF | `pipeline` | 快、稳、CPU 也行 |
| 复杂公式（工科教材） | `vlm-auto-engine` | 视觉大模型，公式识别明显更好 |
| 大量跨页表格、复杂排版 | `vlm-auto-engine` | 版面理解更强 |
| 几百页大书 | `pipeline` | VLM 慢，性价比低 |

## ★★输出可信度红线（实战教训，必读）

**MinerU 输出的表格和公式不能直接当"事实"引用**，尤其在审查、核对、比价、出报告这类"错一个字就出事"的活里。

> **真实案例**：一份边坡地方标准征求意见稿（docx→PDF→MinerU），安全等级表里「很严重 → 一级」被转成「很严重 → 二级」。AI 据此报出"地标违反国标"的重磅意见——**结论是假的，表转错了**。

### 按错型分级

| 错型 | 表现 | 危险度 |
|---|---|---|
| **合并单元格错位** | 纵向合并多的表，某列整体上下漂移一行，**文字全对但归属关系错**；渲染出来毫无违和感，**最会骗人** | ★★★ |
| **公式 OCR** | LaTeX 对错混杂，从输出本身分辨不出来 | ★★★ |
| **比较符退化** | `≤`→`<`、`≥`→`>`，凭空制造"边界缺档"假象 | ★★★ |
| 罗马数字 | `Ⅳ`→`V`、`Ⅲ`→`IⅢ`，制造"缺级/多级"假象 | ★★ |
| 符号丢失 | `°` 丢、下标错乱、`2.5`→`2..5` | ★★ |
| 负号丢失 | 高程 `-6.48` → `6.48`，**整个剖面翻过来** | ★★★ |

### 核对铁律（拿表格/公式内容下结论时）

1. **源头是 docx 的，表格一律回 docx 核对**，别信 MinerU 的 HTML 表。docx 来源的转录，表格甚至可以直接从原文件生成、跳过 OCR。
2. **公式**：定位到原页渲染成图，**肉眼核对原页**。
3. 交付审查/核对类结论时，每条注明「已回原件核实」还是「仅据转录、待核」。
4. ★ 遇到"边界缺档、缺级、表逻辑矛盾"这类反常发现，**先怀疑转录错，后怀疑原文错**。

### ★总原则

> **不要求 100% 准确，要求错误可发现。**
>
> 结构计算要有校核，施工要有验收，试验数据要剔异常——没人指望一次做对，大家指望的是**错了能查出来**。AI 提资料也一样。

## ★★ 转完必须校核（不是可选项）

**核心认知：MinerU 的错，是「看上去完全正常的错」。**

读一遍 md 觉得通顺 = **无效检查**（你自己读不出来，让 AI 读也读不出来）。
要发现不一致，必须引入一个**独立于 MinerU 的第二数据源**来对照。下面所有做法都是这一条的变体。

### 第 0 步：能绕开就别让它出错（优先级最高）

- **源头是 .docx 的**：表格一律回 `word/document.xml` 逐格读（含 `<w:vMerge/>` 合并标记）生成，
  **不要用 MinerU 的表格识别**。MinerU 只负责正文叙述。这条能用就必须用。
- **Word 导出的 PDF（有文本层）**：正文加 `--method txt` 强制走文本提取，不走 OCR，错字率归零。

### 第 1 步：转完立刻跑校核脚本

```bash
<本skill目录>/verify_venv/Scripts/python.exe   <本skill目录>/scripts/verify_transcription.py   --pdf "<原PDF>" --md "<产出.md>" [--md2 "<第二后端.md>"] [--render]
```

⚠ **用的是 `verify_venv`，不是跑 MinerU 那个 `venv`。** pdfplumber 和 mineru 的
pypdfium2/pdftext 版本冲突，必须隔离成两个环境——**绝不要把 pdfplumber 装进 mineru 的 venv**，会把 mineru 搞坏。
装法见上层目录 `README.md`。

产出 `_check_报告.md` + 一份"必看原页"清单。脚本做 5 件事：

| # | 检查 | 抓什么 | 局限 |
|---|---|---|---|
| 1 | 体检 | 整块内容丢失、md 近空、图片 0 张、乱码等事故特征 | 只抓大事故 |
| 2 | 高危 token 逐页对照 | 数字 / `≤≥<>` / 罗马数字 / `°‰㎡` 缺失 → 定位到页 | **只有文本层的 PDF 可用** |
| 3 | 双后端交叉 | pipeline vs vlm 两份 md 对 diff，分歧处=高风险 | 扫描件唯一的自动化手段，耗时翻倍 |
| 4 | 表格结构对照 | pdfplumber 行×列 vs MinerU 表格行×列 | **维度对得上≠内容归属对** |
| 5 | 公式页定位 | 列出含公式的页 + LaTeX 片段数 | **正确性无法自动验证** |

### 第 1b 步：规范/标准类文档，必须再跑骨架校验

```bash
<本skill目录>/verify_venv/Scripts/python.exe <本skill目录>/scripts/check_skeleton.py --md "<产出.md>"
```

**为什么要单独有这一步**：上面那个脚本和"按需核对"都防不住**内容整块丢失**——
丢掉的东西在 md 里**不留任何痕迹**，读起来依然通顺，你根本不会想到去核那一页。

规范类文档有个救命的性质：**条文号/表号/图号是严格连续的**，断号 = 那段没了。纯机器可判、零人工。
输出 `_check_骨架.md`。适用国标/行标/地标/规程，普通图书论文不适用。

**读这份报告的三条要点**：
1. **「疑似误抽」不是错**：MinerU 常把编号和正文连写（`11.9.2` + 正文首字 → 粘成 `11.9.28`），脚本会自动剔除。
2. **断号要回原件确认再下结论**：★ **规范本身就会跳号**。实测 GB 50010 图号从 6.2.11 直接跳到 6.2.15，
   6.2.12~14 原文就不存在。**先怀疑原文跳号，再怀疑转录丢失。**
3. **已知局限**：规范末尾的「条文说明」会重复全部条文号，可能**掩盖正文里的缺失**。要严格查就把条文说明切掉单独跑。

### ★★★ 最要紧的一条：自动校核只能抓到一半

拿一份真实翻车的地标做过回归，**四种错型，自动化只抓到两种**：

| 错型 | 自动化能抓到吗 |
|---|---|
| 比较符退化 `H≤30` → `H<30` | ✅ 检查 2 抓到 |
| 罗马数字错乱 `Ⅲ或Ⅳ` → `IⅢ或IV` | ✅ 检查 2 抓到 |
| **合并单元格错位**（整列安全等级下移一行） | ❌ **完全抓不到**，检查 4 显示行列数**完全一致、判通过** |
| **整行丢失**（表格下面那行"注"） | ❌ 抓不到，pdfplumber 也漏算该行，两边一致 = **假通过** |

> ★ **落点就一句：不是「没做检查」，是「检查通过了，错还在那儿」。**

**必须记住的两条局限**：
1. **行×列一致 ≠ 内容归属正确。** 那张表 19 行里有 12 行的安全等级整体下移了一行，结构维度完全看不出来。
2. **对照双方可能同时漏掉同一处。** 原表实为 20 行（末行是长段"注"），MinerU 和 pdfplumber 都只算 19 行，于是"对上了"。

→ **所以检查 4 通过不构成任何保证。关键的表，只有打开原页看才算数。**

### 第 2 步：看原页（唯一能抓合并单元格错位的手段）

把报告里列出的"必看原页"渲染成图，**逐页比对关键表格**。
表格的**归属关系**（哪个值属于哪一行/哪一列）没有任何自动化手段能保证，只能眼睛看。

### 第 3 步：留痕

在产出目录留一份 `_check_报告.md`，写清**查了什么、哪几页看过原件、还剩哪些没保证**。
下次谁用这份资料，能一眼知道它的可信边界在哪。

## 故障排查

| 报错/现象 | 原因 | 解法 |
|---|---|---|
| `number of pages exceeds limit (200 pages)` | 你用的是**桌面客户端**（云服务配额） | 改用本地版 |
| `CUDA out of memory` | 显存不够 | 换 `--backend pipeline`，或分段 `--start/--end` |
| 首次运行很久没反应 | 在下模型（pipeline ~1GB，vlm ~2GB） | 等着，下完之后秒开 |
| 中文识别错乱 | 语言参数不对 | 确认 `--lang ch` |
| 表格识别差 | 后端不够强 | 换 `--backend vlm-auto-engine` |
| 找不到 mineru | 环境没装 / 装错地方 | 看 `README.md` 重装 |
